# 铁路票务系统开发手册（一期）

> 项目代号：RailTicket；定位：用于 Java 后端实习展示的单体高并发票务系统。
>
> 本文档先固定一期边界和核心规则。所有“后续迭代”内容不应阻塞一期上线。

## 1. 项目目标与范围

系统面向普通用户提供车次查询、余票查看、下单、模拟支付、订单管理和退票能力；面向管理员提供基础车站、车次和票价维护能力。

一期重点是正确处理**区间余票**、**防超卖**、**订单幂等**和**超时回补**，而不是完整复刻 12306。

### 1.1 一期包含

- 用户注册、账号密码登录、JWT 鉴权。
- 常用乘车人维护。
- 按出发站、到达站、乘车日期查询车次和各席别余票。
- 自动分配座位的下单、模拟支付、订单查询、退票。
- 15 分钟未支付订单自动关闭并回补库存。
- 管理端的车站、车次、经停站、运行日期、票价维护。

### 1.2 一期不包含

- 真实支付、实名核验、短信通知、候补购票、改签、复杂选座、跨服务拆分。
- 完整铁路运行图与复杂退改签规则。

## 4. 业务规则

### 4.1 区间余票

一趟车的站点按顺序编号为 `0..n-1`，用户从站点 `i` 乘至站点 `j`（`i < j`）时，实际占用区间为 `[i, j)`，即区段 `i` 至 `j-1`。

- 对某一席别，订单只能在该乘车日期、该车次的每一个途经区段都有余票时创建。
- 创建订单时，对这段区间的所有区段库存各减一；退票和关单时各加一。
- 查询 A → C 的余票时，返回该区间每个区段余票的最小值。
- 一期按“席别库存”售卖，不保存具体座位号；自动分配座位只展示为系统分配。二期再增加物理座位与座位占用区间。

示例：G100 的站点为北京(0) → 济南(1) → 上海(2)。购买北京到上海的二等座，需要同时扣减区段 `0`（北京-济南）和区段 `1`（济南-上海）。

### 4.2 订单状态

```text
PENDING_PAYMENT（待支付） --支付成功--> PAID（已支付）
PENDING_PAYMENT（待支付） --超时/取消--> CLOSED（已关闭，回补库存）
PAID（已支付） --符合退票规则--> REFUNDED（已退款，回补库存）
```

- 仅 `PENDING_PAYMENT` 可支付或取消；仅 `PAID` 可退票。
- 默认支付有效期为创建后 15 分钟。
- 简化退票规则：列车发车前 30 分钟可退票。
- 每次状态迁移必须带前置状态条件，避免并发请求重复回补。

### 4.3 幂等与防超卖

- 创建订单请求必须携带 `requestId`（UUID）。数据库对 `(user_id, request_id)` 建唯一索引；重复请求直接返回已创建的订单。
- 支付、取消、退票和超时关单先通过 `SELECT ... FOR UPDATE` 锁定订单行，在同一事务内完成状态迁移，避免重复回补库存。
- MySQL 使用一条条件更新同时扣减 `[fromStopIndex, toStopIndex)` 的全部区段，条件包含 `available > 0`；影响行数必须等于区段数，否则抛出异常并回滚整个事务。
- Redis 的下单标记只负责快速拦截重复请求；Redis 不可用时降级放行，MySQL 的 `(user_id, request_id)` 唯一索引仍是最终幂等保障。
- 用户查票结果按“始发日期 + 出发站编码 + 到达站编码”整体缓存到 Redis，内容包括起终点、车次时间、席别票价和短时余票快照；默认 TTL 为 10 秒并增加随机抖动。
- 缓存空列表以防止不存在路线反复穿透数据库；缓存未命中时使用 Redisson `RLock` 短期分布式锁限制并发回源，Redis 不可用则直接降级查询 MySQL。
- 每条查票缓存同时登记到“运行计划索引”和“运行计划 + 区段索引”。订单扣减或回补后，只清除与其乘车区间重叠的缓存；库存、票价和运行计划整体变化时，才清除该运行计划的全部缓存。
- 所有缓存失效都安排在数据库事务提交后执行。缓存仅用于展示，下单仍以 MySQL 原子扣减结果为准；极短并发窗口产生的旧快照也会在10～15秒TTL后自动淘汰。
- 订单、状态日志和 Outbox 消息在同一个本地事务提交。RabbitMQ 消息重复消费时，订单状态与行锁保证关单和库存回补幂等；定时扫描负责 MQ 不可用时的最终补偿。

## 5. 数据模型

以下为核心表，统一包含 `id`、`created_at`、`updated_at`；金额使用 `DECIMAL(10,2)`，时间使用 `DATETIME`。为避免与 MySQL 系统表混淆，用户表实际命名为 `sys_user`。

| 表 | 核心字段 | 说明 / 关键索引 |
| --- | --- | --- |
| `sys_user` | `username`、`password_hash`、`role`、`phone` | `username` 唯一 |
| `user_identity` | `user_id`、`real_name`、`id_type`、`id_no`、`status` | 每个账号一条实名信息；证件全局唯一 |
| `passenger` | `user_id`、`name`、`id_type`、`id_no`、`phone` | `(user_id, id_no)` 唯一 |
| `station` | `code`、`name`、`city` | `code` 唯一；`city,name` 索引 |
| `train` | `train_no`、`name`、`status` | `train_no` 唯一 |
| `train_stop` | `train_id`、`station_id`、`stop_index`、`arrival_offset_minutes`、`departure_offset_minutes` | `(train_id, stop_index)` 唯一；时间是相对运行日零点的分钟偏移 |
| `train_schedule` | `train_id`、`travel_date`、`status` | `(train_id, travel_date)` 唯一 |
| `train_fare` | `train_id`、`seat_type_code`、`from_stop_index`、`to_stop_index`、`price` | `seat_type_code` 对应 Java `SeatType` 枚举；`(train_id, seat_type_code, from_stop_index, to_stop_index)` 唯一 |
| `seat_inventory` | `schedule_id`、`seat_type_code`、`segment_index`、`total`、`available` | `seat_type_code` 对应 Java `SeatType` 枚举；`(schedule_id, seat_type_code, segment_index)` 唯一；`available >= 0` |
| `ticket_order` | `order_no`、`user_id`、`passenger_id`、`passenger_user_id`、乘车人快照、`schedule_id`、区间、席别、金额、状态、`request_id`、`expire_at` | `order_no` 唯一；`(user_id, request_id)` 唯一；实名快照建联合索引用于历史车票关联 |
| `order_status_log` | `order_id`、`from_status`、`to_status`、`reason` | 审计订单状态变化 |
| `message_outbox` | `aggregate_id`、`event_type`、`payload`、`status`、`retry_count`、`next_retry_at`、`claim_token` | 订单事务与待发送消息原子提交；状态按 `NEW → SENDING → SENT/FAILED` 流转；`(aggregate_type, aggregate_id, event_type)` 唯一 |

注：一期规定“一笔订单对应一位乘车人、一个席别”。多乘车人合单在二期扩展为订单主表 + 订单项。

### 5.1 数据库脚本与执行顺序

数据库名称固定为 `rail_ticket`，字符集使用 `utf8mb4`。首次本地初始化全新空库时，直接执行 `sql/init_rail_ticket.sql`；该脚本已包含建库、建表、雪花 ID、席别枚举编码和车站乐观锁版本字段。

后续接入 Flyway 后，`db/migration` 下的版本脚本由应用自动执行；在此之前也可以在 MySQL 客户端中手工执行。数据库密码不写入脚本，统一通过 `application-dev.yml` 的环境变量传入。

## 6. 核心流程

### 6.1 查询车次

1. 校验出发地、目的地不同，日期有效。
2. 找到同时经过两站、且出发站序号小于到达站序号的运行车次。
3. 计算每个席别在 `[fromStopIndex, toStopIndex)` 中库存的最小 `available`。
4. 返回车次、发到时间、历时、票价与余票。

### 6.2 创建待支付订单

1. 验证 JWT、`requestId`、乘车人归属、车次运行状态和区间合法性。
2. 若发现同一 `(userId, requestId)` 的订单，直接返回该订单。
3. 通过一条带共享锁的关联查询取得运行计划、车次、出发到达站、车站状态、发车偏移和服务端票价，并确认列车尚未从所选站发车；客户端不提交价格和余票。
4. 开启数据库事务，写入 `PENDING_PAYMENT` 订单并原子扣减全部区段库存；影响行数不等于区段数时回滚。
5. 在同一事务写入状态日志和 `ORDER_TIMEOUT` Outbox 消息；提交后通过专用线程池立即尝试发布，定时扫描继续补偿发送失败或宕机遗留的消息。
6. 立即发布与定时补偿发送前都必须通过条件更新将消息原子抢占为 `SENDING`；`claim_token` 防止旧发布任务覆盖新任务的发送状态，处理租约超时后允许其他实例重新抢占。

### 6.3 实名认证与本人车票关联

- 创建订单时若证件已对应有效实名账号，则将该账号写入 `ticket_order.passenger_user_id`。
- 用户后续完成实名认证时，按姓名、证件类型和证件号码回填尚未关联账号的历史订单。
- 查询本人车票和订单详情时优先使用 `passenger_user_id`，并按实名快照兜底查询 `passenger_user_id` 仍为空的历史订单，以覆盖认证与下单并发产生的漏关联。
- `passenger.id` 始终表示购票人维护的常用乘车人记录，不会被替换为实际乘车人的系统用户 ID。

### 6.3 支付、关单与退票

- 支付：锁定订单行，确认状态为 `PENDING_PAYMENT` 且尚未过期，更新为 `PAID` 并写状态日志。
- 关单：Outbox 消息发布到 `x-delayed-message` 交换机，通过 `x-delay` 延迟到支付期限后投递关单队列；每分钟的数据库扫描作为补偿。两条路径调用同一个幂等方法，锁定订单后仅对已到期的 `PENDING_PAYMENT` 订单回补一次库存。
- 退票：锁定订单行，校验购票人、`PAID` 状态以及距离所选出发站发车至少 30 分钟，更新为 `REFUNDED` 后回补库存并写日志。

## 7. API 约定（一期）

统一响应：`{ "code": 200, "message": "操作成功", "data": {} }`。`code` 与 HTTP 状态码保持一致；业务错误使用 400，未登录使用 401，无权限使用 403，未知服务异常使用 500。写接口建议接收 `Idempotency-Key` 请求头并映射为 `requestId`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/auth/register` | 注册 |
| `POST` | `/api/auth/login` | 登录，返回 JWT |
| `GET` | `/api/stations/suggestions?keyword=上海` | 查询城市和具体车站候选项 |
| `GET` | `/api/trains/search?fromType=CITY&fromValue=上海&toType=CITY&toValue=北京&date=` | 按城市或具体车站查询车次与余票 |
| `GET` | `/api/trains/{scheduleId}` | 车次详情、经停站、票价、余票 |
| `GET/POST/PUT/DELETE` | `/api/passengers/**` | 乘车人管理 |
| `POST` | `/api/orders` | 创建待支付订单；需幂等键 |
| `GET` | `/api/orders` | 当前用户作为购票人的订单列表 |
| `GET` | `/api/tickets/me` | 当前用户作为实际乘车人的本人车票列表 |
| `GET` | `/api/orders/{orderId}` | 购票人或实际乘车人查询订单详情 |
| `POST` | `/api/orders/{orderId}/pay` | 模拟支付 |
| `POST` | `/api/orders/{orderId}/cancel` | 主动取消待支付订单 |
| `POST` | `/api/orders/{orderId}/refund` | 退票 |
| `GET/POST/PUT` | `/api/admin/stations/**` | 管理车站 |
| `GET/POST/PUT` | `/api/admin/trains/**` | 管理车次、站点、运行日和票价 |

创建订单请求示例：

```json
{
  "passengerId": 12,
  "scheduleId": 10001,
  "seatTypeCode": "SECOND_CLASS",
  "fromStopIndex": 0,
  "toStopIndex": 2,
  "requestId": "8bcda84c-8ea7-4d42-88ca-47743d3d65ce"
}
```

## 8. 开发里程碑

| 阶段 | 交付物 | 验收重点 |
| --- | --- | --- |
| M1：基础骨架 | 项目初始化、统一响应/异常、JWT、数据库迁移、Swagger | 可登录，接口可调试 |

## 9. 测试与验收清单

- 同一用户用相同幂等键连续提交两次，只生成一笔订单。
- 库存为 1 时并发创建 20 笔订单，最终仅一笔成功且库存不为负。
- 北京→上海订单占用两个区段；关单/退票后两个区段均正确回补。
- 支付与关单并发执行，订单最终只会落在 `PAID` 或 `CLOSED` 中的一种状态，库存只处理一次。
- 越权访问他人的订单、乘车人或后台接口必须返回拒绝访问。
- 运行数据库迁移后能写入至少 3 个车站、2 趟车、2 个席别和可演示的运行日数据。

## 10. 后续待确认项

开始编码前确认以下选择即可：

1. 使用 Java 21 + Spring Boot 3（已确认）；若后续需要兼容 JDK 8/11，再改为 Spring Boot 2.7。
2. 项目采用 Maven 还是 Gradle（推荐 Maven）。
3. 前端是否自己实现；若不做前端，Swagger UI 足够完成一期演示。
4. 数据库是否已有 MySQL 和 Redis 环境；没有则先用 Docker Compose 或仅 MySQL 完成 M1–M3。
